## 决策

基于 DSH rc.8 的全项目审查,**采用"融合互补"三原则作为插件与官方的长期关系策略**:

1. **官方有且完善 → 直接用官方**(执行引擎 subagent/workflow、user-approval、session/存储/凭据/附件/schedule、client UI/预设 authoring),只做 Consumer,零自建;
2. **官方有接口而实现不完善 → 我们做 Provider/Consumer 提升**(MemberBackend=官方 subagent seam 的组织层镜像、IM 审批呈现、TaskBoard CAS 借官方设计自建、team-state 迁官方 storageDomain、角色资产包=官方 authoring+团队级覆盖注入);
3. **官方缺失 → 我们做深(差异化根据地)**:组织树、IM 入口、绝不 DIY、人机混合替代演进、六条流+五维 scope、三层记忆折叠、Run 面板审计。

同时:**互补共存但一定程度独立/高于官方** —— 官方做"执行与基础设施",我们做"组织操作系统";官方 seam 每强一分,我们多一个可替换的执行引擎,组织语义资产不丢。

## 理由(6 维自评)

- **短中期兼顾**:短期(本次)交付官方能力零成本接入(subagent/workflow 挂预设、CAS 还债);中期(M3)storageDomain 迁移消除自建持久化面;长期 seam 对偶保证官方演进不侵蚀组织语义。
- **拒绝 hack**:不依赖官方 experimental 包(转正会原子重命名);codex/claude 遵循官方"可选 Profile Bundle"协议而非塞进我们 bundle;CAS 借官方设计自建实现而非 import 私有 API。
- **困难留给自己**:跨 profile 预设可见性问题、装配脆弱性、官方团队转正观察——全部封在插件侧(doctor 诊断/文档/升级清单),用户只面对"一条命令 + 一个 profile"。
- **简单留给用户**:FR-D6 派生能力随预设开箱即用;官方 authoring 接管文件级操作,用户不碰 DSH 内部机制。
- **主线回归**:三原则全部服务主线(组织操作系统)——用官方是为执行高效,提升官方是为组织语义完整,做深是为差异化根据地。
- **风险**:官方 experimental team 转正重命名、storageDomain 语义变化、官方未来方向变化 → 均有预案(零依赖/观察一版/每 rc seam 扫描重校)。
